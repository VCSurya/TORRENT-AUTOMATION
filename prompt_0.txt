1. PoNo (List)

A PO number candidate may:

- Be purely numeric (e.g., "33001286", "96", "566")
- OR contain prefixes, division codes, or identifiers
- May include separators like "/", "-", or spaces
 
Examples of valid PO numbers:
- "GJC1/P01/1800618/33001286"
- "KJDH/P01/1865298/96000098"
- "KLJA/J05/1905285/93655196" (From the text: TSSA/P02/1800515/36300777 DTD: 04.06.2024 — ignore all additional text and extract only the PO number)
- "MHPU/P01/1800075/3
   3000011" 
   → If the PO is split across lines (.../3 + next line 3000011), join them to make one complete PO "MHPU/P01/1800075/33000011", not two.
- "33001286"
- "96"
- "566"
- "63364" 

> A PO number is typically a single “identifier-like” token, not a paragraph.
A. Normalization Rules
   1. Treat these HTML entities as equivalent ONLY for label matching:
      "&", "&amp;", "&amp;amp;" → treat all as "&"
   2. Matching is case-insensitive.
   3. Ignore extra spaces and punctuation differences in labels 
      (e.g., "PO No", "PO No.", "P.O No" are equivalent).
   4. The extracted PO value must be returned exactly as it appears in the text, trimming only surrounding spaces or punctuation.
   3. Labels Indicating PO Number
      The following labels may indicate a nearby PO number:
      - Buyer's Order No
      - Buyers Order No
      - Reference No / Reference No. & Date
      - Branch Sole ID / Branch Sole ID Zone
      - Contract / PO Ref
      - Contract Reference
      - Work Order No
      - WO No / W.O No
      - Service Order No
      - Dispatch Doc No
      - Purchase Order No
      - Customer PO No
      - Order Ref
      - PO No / P.O. No / PONO
 
B. Extraction Strategy

   Step A — Global PO Discovery
   1. Scan the ENTIRE text and extract ALL identifier-like tokens that match the PO number definition:
      - Tokens must contain at least one digit
      - Allowed characters: A–Z, a–z, 0–9, "/", "-", space
   2. Tokens may appear:
      - After labels (e.g., "PO No: 33001286", "WO No - TNCH/P01/...")
      - On the same line or the immediately next line
      - Anywhere in the document without labels
   3. Prefer tokens that appear near given labels.

   Step B — Candidate Validation & Cleaning
   1. Trim spaces
   2. Remove surrounding quotes
   3. Remove trailing punctuation: commas, periods, semicolons, brackets
   4. If multiple tokens appear together, split and keep valid PO-like tokens
   5. A valid PO candidate MUST:
      - Contain at least one digit
      - Use only allowed characters (letters, digits, "/", "-", space)
   6. Reject obvious non-PO items:
      - Dates (see Date Rejection Rule)
      - Phone numbers (10+ digit continuous numbers or country-code patterns)
      - Email IDs or URLs
      - Tax IDs (GSTIN, PAN, etc.) when clearly indicated
   7. If unsure, prefer keeping the identifier-like token.

   Step C — Deduplication
   - Remove duplicate PO numbers (case-insensitive)
   - Preserve original formatting as it appears in the text
   
   Step D — Final Output
   - Return ALL valid, unique PO numbers as a list
   - Order of the list should follow first appearance in the text
 
C. Date Rejection Rule
   Reject any candidate matching date-like formats, including:
   - DD/MM/YY, DD/MM/YYYY
   - DD-MM-YY, DD-MM-YYYY
   - DD.MM.YYYY
   - DTD: DD.MM.YYYY
   - D-MMM-YY, DD-MMM-YY, D-MMM-YYYY (e.g., 1-Jan-26, 19-Jan-2026)
   - YYYY-MM-DD, YYYY.MM.DD

**Strict Instruction**:
- Output format MUST always be a list
  - If no valid PO numbers are found: PoNo: []
  - If one or more PO numbers are found: PoNo: ["PO1", "PO2", ...]

6. IrnNo (String)
Goal:
Extract the IRN (Invoice Reference Number) as a single 64-character hexadecimal string.
VALID IRN:
- Exactly 64 characters
- Only hexadecimal characters: 0-9 and a-f (case-insensitive)
- After cleanup (removing spaces/newlines), length must be exactly 64
PRIMARY EXTRACTION (label-anchored, highest priority):
1) Search for an IRN label (case-insensitive):
   "IRN", "IRN No", "IRN No.", "Invoice Reference Number", "IRN Number", "e-Invoice IRN"
2) If found, capture IRN candidate from:
   - The same line after ":" OR
   - The next 1–4 lines immediately following the label
3) Concatenate captured parts by removing:
   spaces, tabs, newlines, ":" and any non-alphanumeric separators.
4) Convert to lowercase for validation.
5) Validate: must match regex ^[0-9a-f]{64}$
   - If valid, output it.
   - If not valid, DO NOT guess; continue to fallback extraction.
FALLBACK EXTRACTION (pattern search):
1) Scan the entire document for any substring matching:
   - 64 hex characters possibly split by spaces/newlines:
     collect sequences of hex chunks [0-9a-fA-F]+ that are adjacent (within 1–2 lines),
     concatenate, then validate exact 64.
2) If multiple valid IRNs found:
   - Choose the one nearest to an IRN label.
   - If none near a label, choose the first occurring valid IRN in the document.
3) If no valid IRN found, return "".
EXCLUSION / ANTI-CONFUSION RULES:
- NEVER treat "Ack. No", "Ack No", "Acknowledgement No", "Ack Date", "eWay No" as IRN.
- Do not output any number unless it validates as 64-hex exactly.
- If the captured string contains any characters outside [0-9a-fA-F] after cleanup, it is invalid → return "".
OPTIONAL OCR REPAIR (use ONLY if you allow deterministic correction):
If candidate is found next to an IRN label BUT fails validation due to common OCR confusions,
apply ONLY these replacements BEFORE final validation:

- Replace 'o'/'O' → '0' ONLY if it makes the result pass ^[0-9a-f]{64}$
- Replace 'i'/'I'/'l' → '1' ONLY if it makes the result pass ^[0-9a-f]{64}$

Rules:
- Apply replacements only within the extracted IRN candidate (not the whole document).
- After replacements, validate again with ^[0-9a-f]{64}$.
- If still invalid, return "" (no further guessing).

7. SesGrn (List)
Extract SES / GRN / Service Entry Sheet / Scroll numbers.

A) LABEL-ANCHORED EXTRACTION (STRICT ±1 LINE WINDOW, OCR-ROBUST)
Look for these labels (case-insensitive, allow punctuation/spaces):
- "SES No", "SES#", "Service Entry Sheet", "Service Entry No", "SE No", "SE#"
- "GRN No", "GRN#", "GRN / SE No", "GRN /SE No", "Goods Receipt No"
- "Scroll No", "Scroll#"

For each label occurrence, search ONLY within the 5-line window:
- two line above the label line,
- the label line itself,
- two line below the label line.

Extraction rules (within the window only):
1) SAME-LINE AFTER-SEPARATOR RULE:
   On the label line, if ANY of these separators appear after the label text:
   ":"  OR  "-"  OR  "–"  OR  "—"
   then take the text AFTER the FIRST occurring separator on the SAME line.
   - Trim spaces.
   - If the taken text is empty or fails validation, treat as "nothing valid on label line".

2) SAME-LINE EMBEDDED-DIGITS RULE (OCR merged lines):
   If rule (1) does not yield a valid candidate, but the label line contains digits anywhere,
   then take the substring on the label line that starts at the FIRST digit to the end of line.
   - Trim spaces.
   - Validate it (see Validation below).
   - This rule is ONLY for the SAME label line (still within ±0 line).

3) ONE-LINE-BELOW RULE:
   If nothing valid on the label line, then check the ONE line below the label line
   and take the full line as candidate (trim spaces).

4) ONE-LINE-ABOVE RULE:
   If still nothing valid, then check the ONE line above the label line
   and take the full line as candidate (trim spaces).

Non-negotiable:
- Do NOT read 2+ lines below or above. Only the ±1 line window.

VALIDATION FOR A (keep light but practical):
Accept candidate if ALL are true:
- contains at least one digit
- total length between 3 and 30 (after trimming)
- NOT a Date-like pattern (reject if matches dd/mm/yy, dd/mm/yyyy, dd.mm.yyyy, yyyy-mm-dd, or contains month names with a year)
- NOT a Phone-like pattern (reject if contains "+" and 8+ digits, or contains 10+ digits with spaces typical of phone)
- if "Po No:" appears with hyphenated digits-digits pattern (e.g., 3-456) must ne selected as SesGrn. 

Soft clean-up (allowed, within extracted candidate only):
- Trim leading/trailing punctuation like ":" "-" "–" "—" "." "#" and spaces.
- Do NOT concatenate multiple lines.
- Do NOT expand the search window.

Optional (ONLY if you want split values):
- If candidate contains "/" or "," or "-" between digit groups (e.g., "6000138012 / 6000138017","6000138012 - 6000138017"),
  you MAY either:
  (a) keep as-is as one entry, OR
  (b) split into separate entries by "/" or "," or "-" and keep only pieces that pass validation.
(Choose one behavior and apply consistently.)

B) RECEIVING/POSTING BLOCK OVERRIDE (DCC rule, STRICT ±1 LINE WINDOW)
Trigger condition:

Then, ONLY within the 1-line window around that label (above, same, below):

  - Must contain EXACTLY ONE hyphen
  - No letters allowed
  - No extra hyphens, slashes, spaces, or punctuation inside the token
  - If "DCC Control" appears anywhere, then any hyphenated digits-digits pattern (e.g., 3-456) outside the 3-line window around "DCC  Control" must be selected as SesGrn.

IMPORTANT:

C) DEDUPLICATION
Remove duplicates while preserving first appearance order.
If nothing found, return [].

VALUE NORMALIZATION (REQUIRED SPLIT FOR MULTI-VALUES)
After a candidate is accepted by Validation A, normalize it:

1) Remove leading/trailing punctuation and spaces: ":" "-" "–" "—" "." "#" and whitespace.

2) If the candidate contains multi-value separators such as "/" or "," or ";" or "|" or multiple spaces,

3) For each split part:

   - If a part contains extra non-digit characters surrounding digits, keep the full part ONLY if still passes Validation A.

4) Add each kept part to SesGrn in the same left-to-right appearance order.

If splitting produces zero valid parts, fall back to the original candidate as-is (only if it passed Validation A).
